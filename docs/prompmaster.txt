0. HOW TO USE THIS DOCUMENT
--------------------------------------------------------------------------------

0.1  You are an autonomous build agent. Your task is to implement (or re-skin and
     extend) the full Android application described here, exactly as specified.
     Every numbered requirement is BINDING. Where a value is prescribed (a hex
     colour, a port, a string, a behaviour, a formula), reproduce it precisely —
     do not substitute your own taste. Where nothing is prescribed (XML layout
     syntax, class internals, coroutine plumbing), choose the SIMPLEST
     implementation that satisfies every requirement and still runs on the oldest
     supported device.

0.2  Order of authority when two sources disagree:
        1. This document.
        2. The UI mock deck shipped with this document (see Appendix C).
        3. The reference drafts named in the header (background only).
        4. Anything else.

0.3  The UI mock deck is the visual source of truth for layout, copy, colour and
     information hierarchy. It exists in TWO complete renderings — a dark set
     (a-series files) and a light set (b-series files). Both are shipping themes,
     not concept art. See §4.1.

0.3.1 THE MOCKS CARRY AN OLD WORDMARK. The deck was drawn for the earlier
     MorseLink project, so some frames print "MorseLink" — onboarding slide 4's
     button, the Help accordion's first question, the log-viewer header line,
     the "MorseLink" media folder in the Videos/WebShare folder panels, and the
     sample log version "1.5.1 (15)". Read every one of those as "Morsecode"
     and 1.0.0 (1) respectively (§1.1, §19.1). This is the ONE respect in which
     this document deliberately overrules the artwork; everything else about
     the mocks stands as drawn.

0.4  Mock chrome that is NOT app UI and must NOT be implemented:
        - the drawn phone bezels / notches / rounded device frames,
        - the deck captions ("02 — the hub", "05 — dashboard · preferences", …),
        - the floating "Dark | Light" pill in the top-right of some sheets,
        - the fake status-bar network-speed readout ("12.4K/s") — that is the
          reference phone's own MIUI/EMUI status bar, not a Morsecode feature.

0.5  Tags used below:
     Everything in this document is being built from zero; the tags record
     PROVENANCE, not migration state:
        [NEW]      no prior art in either reference draft — design it from this
                   document alone.
        [CHANGED]  the reference drafts specified something different; this
                   document overrides them. Do not "restore" the old behaviour.
        [KEPT]     carried forward from the reference drafts on purpose — the
                   rationale is hard-won (usually a real field defect). Treat a
                   [KEPT] rule as release-blocking and do not "improve" it.
        [GAP]      the mocks were silent or self-contradictory here; this
                   document decides. All [GAP] decisions are listed in Appendix D.

0.6  Build order that works: platform rules → design system → navigation shell →
     transfer engine (1:1) → transports → screens → broadcast → WebShare →
     diagnostics → release. Ship nothing that fails §22.

1. PRODUCT IDENTITY
--------------------------------------------------------------------------------

1.1  NAMES. The repository/project is "morsecode". The product, the launcher
     label, the store listing, every user-visible string, the log header and the
     notification titles all say "Morsecode" — one word, capital M only. Never
     "Morse Code", never "MorseCode", never "MorseLink". Named after Morse code:
     communication without infrastructure.

1.1.1 NAMING IS SINGLE-SOURCE. This is a NEW project. There is no shipped
     predecessor to update, no installed base to migrate, no legacy peer to
     interoperate with and therefore NO compatibility shims anywhere. Nothing —
     no string, identifier, folder, scheme, magic number or class name —
     contains "MorseLink" or "morselink". Use exactly these:

       applicationId / root package  app.morsecode.android
       Application class             MorsecodeApp.kt
       Launcher label / app_name     Morsecode
       versionName / versionCode     1.0.0 / 1  (§19.1)
       Wire chunk magic              "MRSC" (4 bytes, §11.3)
       Nearby service id             app.morsecode.android.nearby
       Deep-link scheme              morsecode://<host>:<port>  (typed or
                                     pasted only — there is no QR, §11.5)
       Partial-download suffix       <name>.morsecode.part              (§9.4)
       Default media folder          Download/Morsecode                 (§12.4)
       Notification channel ids      morsecode.transfer · morsecode.webshare
       Exported log header           Morsecode <version> (<versionCode>)
       Signing key                   generate a fresh upload key for this repo;
                                     there is no existing key to preserve.

     Ports are 33455 (WebShare) / 33456 (TCP control+data) / 33457 (UDP
     discovery) — chosen values, not inherited constraints; keep them so the
     mocks, the docs and the firewall guidance agree.

     FORWARD compatibility only: HELLO carries protocolVersion, which starts at
     1 and exists so that a FUTURE Morsecode release can refuse or adapt to an
     older one (§11.6). It is not a backward-compatibility promise to any other
     product. If you find yourself writing a branch that reads a legacy format,
     delete it — the case cannot occur.

1.2  Pitch (one line, used in store copy and onboarding slide 1):
     "Offline, peer-to-peer file transfer for Android. No cloud, no internet, no
     accounts, no ads, no analytics."

1.3  FOUR transfer surfaces (was three):
     S1  Phone ↔ Phone over Wi-Fi LAN — both devices on the same router or
         hotspot. The fast path and the default.
     S2  Phone → many phones ("Broadcast") over Wi-Fi LAN or Nearby — one sender
         fans the same queue out to up to 8 receivers at once.            [NEW]
     S3  Phone ↔ Phone over Google Nearby Connections (Bluetooth / Wi-Fi Direct)
         — the zero-infrastructure path when there is no shared network.
     S4  Phone ↔ browser over WebShare — the phone runs an HTTP server on
         :33455; any laptop or second phone on the same network browses,
         downloads, plays and uploads.

1.4  Target user and hardware. Someone with an old, low-RAM phone in a
     connectivity-poor environment. The PRIMARY reference device is a HUAWEI
     MYA-L10 on Android 6.0 (API 23) — every flow must complete end to end on it.
     The SECONDARY reference device is a current Android 14/15 phone. minSdk 21.
     Everything degrades gracefully; nothing functional is ever switched off
     because a device is slow (§13).

1.5  Design language [CHANGED]. Sunflower on near-black, or sunflower on warm
     paper. One accent colour at a time, user-selectable from five. Flat cards
     with hairline borders, generous touch targets, monospaced technical meta,
     no shadows in dark mode, soft shadows in light mode. Calm, technical,
     trustworthy. Custom lightweight widgets; no heavy UI framework. The app must
     feel instant on a 2016 phone.

1.6  Explicitly NOT in scope. Do not build, do not scaffold, do not hint at in
     UI copy: contacts/vCard sharing; phone-clone/SMS/call-log migration; junk
     cleaner or cache scanner; WhatsApp-status scraping or any browse of another
     app's /Android/data/<pkg> sandbox; media converters; cloud backup or sync;
     a native desktop app; any ad SDK, sponsored app row, or interstitial; any
     analytics, attribution or telemetry SDK; any "connect to a stranger",
     public/temporary-link or internet relay feature.
     NOTE: "multi-device group send" was previously on this exclusion list. It is
     now a headline feature (§10). The exclusion is deliberately revoked.

1.7  Monetisation. None. No ads ever. If money is ever needed it is a single
     one-time "Pro" unlock — never ads, never data, never fake urgency.

3. HARD PLATFORM RULES (never violate)
--------------------------------------------------------------------------------

3.1  Kotlin. Single `:app` Gradle module, manual service locator
     (`di/AppServices.kt`), no DI framework, no annotation processors beyond
     AndroidX defaults. (If the build is ever split into modules, §20.7's
     cross-module rules become binding; until then they are dormant.)

3.2  minSdk 21, targetSdk 34+, compileSdk latest stable. ALL runtime code must be
     API-23-safe: every API above 23 is version-checked; nothing crashes on
     Android 6. Java-8 default collection methods (`removeIf`, `putIfAbsent`,
     `computeIfAbsent`, `Stream`) require API 24 AT RUNTIME regardless of
     compileSdk — guard each one with `Build.VERSION.SDK_INT >= 24` and a manual
     loop fallback. This is enforced by the lint gate in §20.8.

3.3  Third-party budget: total APK growth from non-AndroidX libraries ≤ 5 MB.
     The allowed set is exactly: AndroidX, Google Play Services Nearby
     Connections and NanoHTTPD. Nothing else. No image-loading library
     is required (thumbnails go through MediaStore + a small LRU bitmap cache);
     if one is used it must fit the 5 MB budget.

3.4  No network egress except the local network. No analytics, no crash upload,
     no update ping, no font/CDN fetch. Crash reports and logs never leave the
     device unless the user exports them by hand.

3.5  Manifest permissions — exactly this set, no additions:
       INTERNET, ACCESS_NETWORK_STATE, ACCESS_WIFI_STATE, CHANGE_WIFI_STATE,
       CHANGE_WIFI_MULTICAST_STATE, WAKE_LOCK
       ACCESS_FINE_LOCATION (maxSdkVersion 30)
       BLUETOOTH + BLUETOOTH_ADMIN (maxSdkVersion 30)
       BLUETOOTH_SCAN + BLUETOOTH_ADVERTISE + BLUETOOTH_CONNECT (31+, neverForLocation)
       NEARBY_WIFI_DEVICES (33+, neverForLocation)
       READ_EXTERNAL_STORAGE (maxSdkVersion 32), WRITE_EXTERNAL_STORAGE (maxSdkVersion 28),
       MANAGE_EXTERNAL_STORAGE, READ_MEDIA_IMAGES, READ_MEDIA_VIDEO,
       READ_MEDIA_AUDIO, READ_MEDIA_VISUAL_USER_SELECTED
       POST_NOTIFICATIONS, FOREGROUND_SERVICE, FOREGROUND_SERVICE_DATA_SYNC,
       REQUEST_INSTALL_PACKAGES, REQUEST_IGNORE_BATTERY_OPTIMIZATIONS
       (CAMERA is NOT declared — there is no QR scanner, §11.5)
     Do NOT declare CHANGE_NETWORK_STATE or anything not on this list. Wi-Fi and
     Bluetooth hardware features are declared `required="false"`.
     MANAGE_EXTERNAL_STORAGE is never requested at launch or during onboarding —
     it is an optional, explained upgrade from Settings only (§12.3).

3.6  `MainActivity` handles ACTION_SEND and ACTION_SEND_MULTIPLE (`*/*`): shared
     items queue straight into the send flow with the destination unresolved.

3.7  A foreground service (`dataSync`) owns every active session so minimising,
     rotating or navigating away never interrupts a transfer. Battery-optimisation
     exemption is requested with an explanation, never silently, never required.

3.8  Every user-visible string lives in `strings.xml`, correctly escaped
     (apostrophes as \'), no duplicate names, no hardcoded text in layouts or
     Kotlin. Appendix A is the authoritative copy list.

3.9  `networkSecurityConfig` permits cleartext for local/private ranges only
     (WebShare needs it from API 28 on).

4. DESIGN SYSTEM  ("Sunflower")
--------------------------------------------------------------------------------

4.1  THEMES. Three user choices: Light, Dark, Follow system. First run resolves
     to the system setting; if the system has no preference, Dark. Both themes
     are complete: every screen, dialog, sheet, notification and the WebShare
     web UI must render correctly in both. Theme switching is instant and
     preserves scroll position and transfer state.

4.2  COLOUR TOKENS — DARK (sampled from the a-series mocks, exact):
       bg/base                #0B0B0B
       surface/card           #141414
       surface/raised         #1A1A1A   (sheets, dialogs, chips, inputs)
       surface/pressed        #1F1F1F
       hairline/divider       #1F1F1F
       text/primary           #F5F5F4
       text/secondary         #A1A1AA
       text/meta (mono)       #71717A
       scrim                  #000000 @ 62%

4.3  COLOUR TOKENS — LIGHT (sampled from the b-series mocks, exact):
       bg/base                #EEEDE7   (warm paper, NOT pure white)
       surface/card           #FFFFFF
       surface/raised         #F5F4EE
       surface/pressed        #E9E8E3
       hairline/divider       #E4E1D8
       text/primary           #141310
       text/secondary         #6B6862
       text/meta (mono)       #8A867E
       scrim                  #141310 @ 38%
       Light-mode cards carry a 1 dp #E4E1D8 border AND a 2 dp/4% soft shadow;
       dark-mode cards carry the border only (never a shadow).

4.4  ACCENT PALETTE. Exactly five swatches in Settings, in this order; the first
     is the default:
       1 Sunflower  #FACC15   (pressed/gradient-end #EAB308, deep #A16207)
       2 Leaf       #84CC16   (pressed #65A30D)
       3 Ember      #EA580C   (pressed #C2410C)
       4 Violet     #8B5CF6   (pressed #7C3AED)
       5 Sky        #0EA5E9   (pressed #0284C7)
     Ink on any accent fill: #1A1400 in light-on-accent situations, i.e. always a
     near-black, never white — the accents are bright.
     The accent tints: primary buttons, selected nav/tab, progress fill start,
     radar, links, focus rings, chip outlines, the profile avatar, the accent
     wash on summary cards. It NEVER recolours the launcher icon or the logo.
     Accent wash (used by every "summary" card): accent @ 8% fill + accent @ 35%
     1 dp border in dark; accent @ 14% fill + accent @ 45% border in light.

4.5  SEMANTIC COLOURS (identical in both themes, these do NOT follow the accent):
       success / verified / DONE / Accept / "Send (n)" pill   #22C55E
       receiving (RECV chip, incoming rows)                    #A78BFA on #412D6D
       sending / in-progress                                   current accent
       paused / warning                                        #F59E0B
       failed / error / End session / Reject-destructive       #EF4444
       neutral chip                                            surface/raised + text/secondary
     Progress fill is a left-to-right gradient from the accent to #84CC16;
     a COMPLETED bar is solid #22C55E; a PAUSED bar is solid #F59E0B; a FAILED
     bar is solid #EF4444 at 40% width-frozen.
     The WebShare storage bar is a three-stop gradient #FACC15 → #EA580C → #22C55E.

4.6  PEER IDENTITY COLOURS. Every peer gets a letter avatar (first letter of its
     device name, uppercase) on a deterministic colour chosen by
     `abs(deviceId.hashCode()) % 6` over this fixed palette — independent of the
     accent so peers stay distinguishable:
       #F59E0B (amber) · #8B5CF6 (violet) · #0EA5E9 (sky) · #22C55E (green) ·
       #EF4444 (red) · #EC4899 (pink)
     The mocks' M/R/P/S avatars (MYA-L10 amber, Ravi's Redmi violet, Pixel 7X sky,
     Samsung A14 green) must reproduce exactly for those names.

4.7  TYPOGRAPHY. System family (Roboto). A second face, the system MONOSPACE, is
     used for all technical meta — this is a defining part of the look.
       screen title            20 sp  medium
       section header          11 sp  medium, UPPERCASE, +0.08 em, text/secondary
                                      ("ACCENT COLOUR", "DISCOVERED", "SYSTEM")
       list item title         15 sp  medium
       list item meta          12 sp  MONO, text/meta  ("4.1 MB · queued")
       state chip              10 sp  MONO, UPPERCASE, +0.06 em
       body / FAQ answer       14 sp  regular, 1.45 line height
       button label            14 sp  medium, sentence case
       stat tile value         20 sp  bold, accent
       stat tile label          9 sp  MONO, UPPERCASE, text/meta
       log line                11 sp  MONO
     All sizes in sp, never dp. Layouts must survive the largest system font
     scale without hiding a file name, percentage, state or button label; long
     file names use MIDDLE ellipsis so the extension always stays visible.

4.8  SPACING, SHAPE, ELEVATION.
       base unit 8 dp · screen padding 16 dp · list row vertical padding 12 dp
       card radius 16 dp · sheet radius 20 dp (top only) · dialog radius 20 dp
       chip radius 8 dp · thumbnail radius 10 dp · avatar radius full circle
       primary button radius 14 dp (rectangular-rounded, NOT a pill — the mocks'
         "Continue" / "Grant permissions" buttons are 14 dp)
       segmented control radius full pill (History Received/Sent)
       minimum touch target 48 × 48 dp everywhere, achieved with padding, never
         by inflating the icon artwork.

4.9  ICONOGRAPHY. One outlined set, 24 dp, 2 dp stroke, currentColor. Category
     and onboarding icons are the only filled artwork: solid rounded squares
     (22% radius) with a white glyph, one colour per concept —
       onboarding: radar #F59E0B→#EA580C, lock #22C55E, globe #0EA5E9, check #8B5CF6
       file types: image #F59E0B, video #0EA5E9, audio #A78BFA, doc #22C55E,
                   archive #EF4444, apk #8B5CF6, unknown #71717A
     Every icon-only control ships a contentDescription (§15.1).

4.10 LOGO / LAUNCHER ICON. A squircle tile with a warm orange gradient
     (#EF7D0F → #F5A712 → #FBBF24, 135°) carrying a black Morse glyph: three
     heavy vertical bars on the left, six dots in a 2 × 3 grid on the right, and
     one long horizontal bar underneath — as in logo.PNG. Ships as adaptive
     (foreground + #F5A712 background), legacy, and round mipmaps at every
     density, in EVERY build. A default template icon is a release blocker. The
     logo never takes the accent colour.

4.11 MOTION. Radar sweep 2.4 s linear with 3 pulsing blips (1.6 s). Progress bars
     lerp to their new value over 150 ms rather than jumping. Chips crossfade
     120 ms. Sheets spring in 220 ms. Everything obeys
     `Settings.Global.ANIMATOR_DURATION_SCALE`; on a low tier device (§13) the
     radar degrades to a static ring + "Searching…" and progress animation is
     disabled.

4.12 CORE COMPONENTS (build once, reuse everywhere):
     a) PeerCard — avatar, name, "Connected · Phone · LAN" mono subtitle, right
        transport badge (LAN / NEARBY / WEB / FROM). Used on transfer, receive,
        broadcast and complete screens.
     b) TransferRow — type icon tile, file name, mono meta line
        ("48.9 / 144 MB · 6.2 MB/s"), right state chip, thin progress bar
        underneath, optional trailing ✕. Variants: sender, receiver, per-peer
        sub-row (indented, avatar instead of icon tile, right-aligned percent).
     c) SummaryCard — accent-wash card with a title line ("Batch in progress",
        "✓ Batch complete", "Broadcasting to 3 phones"), a mono detail line, and
        an optional row of up to three StatTiles.
     d) StatTile — value + mono uppercase label on surface/raised.
     e) ActionBar — 5 evenly spread tiles: Choose (+, accent-washed tile),
        Queue (☰), Pause (❚❚), Minimize (—), End (✕, #EF4444). Labels always
        visible under the icons.
     f) BottomNav — Connect (◎) · Files (▭) · History (◷) · Settings (≡);
        selected item gets an accent-washed rounded tile behind the icon and an
        accent label.
     g) StateChip, SectionHeader, EmptyState (icon + line + action), Tip
        (dismissible one-time hint), ConsentDialog, BottomSheet.

4.13 HARD UI RULES.
     - Status is NEVER communicated by colour alone: every state has a chip with
       a word (QUEUED / SENDING / RECV / PAUSED / DONE / FAILED / SKIPPED) or an
       icon plus a label.
     - One accent at a time across the whole product, including WebShare. Green,
       violet, amber and red appear only with their §4.5 semantic meaning.
     - Confirm before Material widgets: check what the base theme actually
       inherits from (MDC-2 vs M3) and use the matching widget variant. A switch
       that renders 0 dp tall is a theme-ancestry bug, not a logic bug.
     - No screen may hard-code a hex value; everything resolves through the token
       names above so the accent picker and the light theme keep working.

4.14 RESPONSIVE LAYOUT — ONE UI, EVERY SCREEN SIZE [CHANGED]
     Nothing in this product may assume a 360 dp phone. Every screen is built
     from fluid containers and verified at, at minimum:
       · 320 dp (small phone) · 360–412 dp (mainstream) · 480 dp (large phone)
       · 600 dp (small tablet / split-screen) · 840 dp+ (tablet, foldable open)
       · landscape at each of those, and at the largest system font scale.
     Rules:
       - No fixed pixel widths for content. Grids use an adaptive column count
         (e.g. GridLayoutManager with a target cell width: 3 columns at 360 dp,
         4 at 480 dp, 6+ on a tablet) rather than a hard-coded span of 3.
       - Rows, sheets, dialogs and the selection bar stretch to the container
         and cap their maximum width on wide screens instead of spanning a
         metre of tablet.
       - Tab strips, segmented controls and action bars distribute their cells
         evenly and never leave dead space at one edge.
       - Text wraps or ellipsises; nothing is clipped, and no layout scrolls
         horizontally unless it is explicitly a carousel.
       - Foldables and split-screen: re-layout on configuration change with all
         state (selection, scroll, zoom, playback) intact; the transfer engine
         never restarts because the window resized.
       - WebShare's pages are responsive too: the rail collapses, the folder
         panel becomes a horizontal chip strip and low-value table columns
         (Modified) drop out on narrow viewports — a phone browser must be able
         to use the site (§7.5).

5. INFORMATION ARCHITECTURE
--------------------------------------------------------------------------------

5.1  Exactly four bottom tabs, no secondary shortcut row, no "AI" entries:
        [ Connect ]   [ Files ]   [ History ]   [ Settings ]
     Every tab must open without crashing; a crashing tab is a release blocker.

5.2  Navigation map.
        Connect (dashboard)
          ├─ Send            → Discovery → Transfer(SENDING)
          ├─ Receive         → Receive(listening) → Transfer(RECEIVING)
          ├─ Broadcast       → Discovery(multi-select) → Broadcast(sender)
          ├─ WebShare card   → WebShare screen (start/stop, URL, sessions)
          ├─ Recent device   → reconnect → Transfer
          └─ ? (help)        → Help & FAQ / Connection Doctor
        Files (Photos · Videos · Music · Apps · Files)
          ├─ selection bar   → Send (n) → Discovery/attach to session
          ├─ item tap        → Viewer / Music player / Video player
          └─ Add a folder    → SAF tree grant
        History (Received | Sent)
        Settings → Logs · Connection Doctor · Help & FAQ · Replay onboarding
        Overlays: Queue sheet · Consent dialogs · Conflict dialog · Batch summary
     Transfer, Broadcast, Viewer and the players are full destinations that KEEP
     the bottom nav visible; the tab you launched from stays highlighted (this is
     why the mocks show "Files" lit during a transfer).

5.3  Back / Minimize / End.
       Back on a transfer screen = Minimize (session survives in the service).
       Minimize = same, and returns to where you came from.
       End = confirm dialog ("End this session? Queued files will be paused.")
             then a clean BYE to every peer.
       Back must always fall back to popping the stack when there is no sensible
       up-target (covers the post-crash relaunch state).

5.4  A screen's purpose is always passed as an explicit navigation argument
     (SENDER / RECEIVER / BROADCAST / RESUME) — never inferred from incidental
     state such as "is something queued right now".

         type="range"> with ← → stepping 5 s, Home/End jumping to start/end, and
         an announced value ("2 minutes 43 seconds of 4 minutes 8 seconds");
       · the ±10 s buttons are real seeks against the same state — they clamp at
         0 and at the duration and never wrap around;
       · seeking while paused keeps the player paused and repaints the frame at
         the new position; seeking past the end ends the item cleanly.

7. WEBSHARE — PHONE ↔ BROWSER
--------------------------------------------------------------------------------

7.1  SERVER.
     NanoHTTPD bound to 0.0.0.0:33455, started and stopped ONLY by explicit user
     action (dashboard card pill, or the WebShare screen's Start/Stop).
     INV-4 (no idle shutdown) [KEPT]: the server stays up until the user stops
     it. No idle timeout, no auto-teardown, screen-off is never a reason to
     close, and it never shuts down while a browser session is connected.
     The address is a bare IP:port with NO token in the URL
     (http://192.168.1.24:33455). Access control is consent-based: a new browser
     session sees only a waiting screen until the phone's owner accepts (§6.16b);
     on accept the server issues a session token that every subsequent API call
     must carry (header or query param); a request without a valid, unexpired
     token gets 401. The token dies when WebShare stops or the session is
     revoked. Sessions are listed on the WebShare screen with a Revoke action.
     The server runs alongside the foreground service with its own persistent
     notification showing the URL. Every response carries `Cache-Control:
     no-store` — the web UI is compiled into the APK and a cached copy of an old
     build silently breaking against new server logic has bitten us before.
     Optional hotspot mode (HotspotController): API 26+ uses
     LocalOnlyHotspotReservation and shows the generated SSID/password as large,
     monospaced, tap-to-copy text; API 21–25 deep-links to wireless settings,
     polls for the AP, then reads the gateway (typically 192.168.43.1 — which is
     why one mock's URL is http://192.168.43.1:33455). If the phone is currently
     on Wi-Fi, confirm first: "Starting the hotspot will disconnect you from
     'MY-NETWORK'. Continue?" — STA and AP share one radio on this hardware
     range. mDNS via NsdManager is a convenience only and always holds a
     MulticastLock; the raw http://ip:port is always shown as plain text too.

7.2  ENDPOINTS.
       GET  /                      single-page app (self-contained, no CDN)
       GET  /api/hello             handshake → pending | accepted | rejected
       GET  /api/info              device name, model, OS
       GET  /api/counts            per-category counts + storage used/total
       GET  /api/files             category | folder | search | sort | cursor | pageSize
       GET  /api/fs                filesystem browse (path, breadcrumb, entries)
       GET  /thumbnail             sized, server-cached thumbnails (id + mtime key)
       GET  /download              streams a file, MUST support Range
       GET  /download-file         raw file by path
       GET  /download-folder       streamed ZIP64 of a folder
       GET  /download-zip          streamed ZIP64 of a selection
       GET  /video/<name>          the in-browser player page (§7.6)
       GET  /stream                byte-range media stream for the player
       POST /upload                chunked upload (§7.7) + small-file multipart
       GET  /api/upload-status     per-file chunk progress
       GET  /api/events            SSE: push offers, consent changes, counts
       POST /api/push-accept       browser accepts a phone→browser push (§7.8)
     Zip streaming is built through a pipe as it is sent (never fully assembled
     first), is ZIP64-capable (>4 GB, >65 535 entries), sets the UTF-8 name flag,
     and aborts generation the moment a broken pipe says the client is gone.
     /upload writes into the user's chosen destination, inserts into MediaStore
     where applicable, and returns the ACTUAL bytes written and saved path —
     never a hardcoded success. The multipart parser's pushback buffer must be
     at least as large as the read chunk size, or trailing bytes are silently
     dropped and uploads arrive truncated.

8.2  PRINCIPLES.
     - TransferEngine is the single source of truth for queue and session state.
       It exposes StateFlows (items, session, peers) and a shared EngineEvent
       flow (PeerConnected, PeerDisconnected, BatchCompleted, PeerDelivered…).
       Fragments observe and render; they never own transfer state.
     - Coordinators are process-scoped. Incoming file handling is owned by the
       engine/service, never by a screen — a session whose incoming stream is
       only collected while a fragment is visible will handshake, look connected,
       and silently receive nothing.
     - TransportSession abstracts one connected peer: sendFile(item, sha),
       pauseOutgoing(fileId), cancelTransfer(fileId), close(reason), plus
       incoming callbacks. Implementations: LanSession, NearbySession,
       WebPeerSession. The engine is transport-agnostic.
     - Journal persistence: the outgoing queue and in-progress receives are
       journaled on EVERY state transition so a crash or force-kill never loses
       the queue.
     - Any state the UI must react to is a Flow, never a plain field; and a flow
       that starts at `false` must be distinguishable from "was true, then
       ended", so a fresh screen never announces "connection closed".
     - One-shot events (navigate back, show summary) are delivered through a
       consumable event wrapper — a replayed LiveData value must never re-fire a
       navigation.
     - DeviceTier (§13) scales pre-hash limits, thumbnail sizes, page sizes,
       thread pools and animation; never functionality.

9. TRANSFER ENGINE — EXACT SEMANTICS (1:1)
--------------------------------------------------------------------------------

9.1  ITEM MODEL.
     TransferItem(id, batchId, direction SENDING|RECEIVING, state, file{displayName,
     uri, mime, size}, relativePath?, totalBytes, bytesTransferred, speedBps,
     resumeOffset, retryCount, lastError, peerId?)
     States: QUEUED → IN_PROGRESS → COMPLETED | SKIPPED | PAUSED | CANCELLED | FAILED

9.2  THE OUTGOING WORKER — the most important loop in the app.
     Exactly ONE worker coroutine per session picks the first QUEUED send and
     calls session.sendFile(item, sha).
     INV-9 NEVER SCROLL THE USER BACK TO THE TOP [CHANGED]. Ticking a checkbox,
     starting playback, a progress update or any other state change must leave
     every scroll container exactly where it was — phone lists, the WebShare
     content pane and the file tables alike. Re-rendering a whole list on each
     state change is allowed only if the scroll offset is captured and restored
     (or the update is applied in place). Losing the scroll position after
     selecting the 40th file is the single most-reported annoyance of this kind
     of UI and counts as a bug, not a redraw artefact.

     INV-1 NEVER HANG. The worker must never wait forever:
        (a) session close/disconnect immediately completes ALL pending send
            waiters with a failure result;
        (b) every pause/cancel path schedules a 3-SECOND TERMINAL FALLBACK that
            force-completes the waiter when no transfer update arrives (several
            OEM stacks never emit a terminal update after a cancelled payload);
        (c) the await itself is bounded.
     INV-2 PAUSE/CANCEL NEVER BLOCKS OTHERS. Pausing or cancelling one file
        affects only that item; the worker returns and picks the next queued file
        within seconds.
     INV-3 SESSION RESTART UNSTICKS EVERYTHING. When a session is lost, all
        IN_PROGRESS and QUEUED sends become PAUSED with "Connection lost" —
        never stuck, never failed. When a new session is established, all PAUSED
        sends are automatically re-queued and resumed from resumeOffset.

9.3  OUTCOMES AND RETRY. sendFile returns Completed | SkippedAlreadyPresent |
     Paused | Cancelled | Failed(error).
       Failed + session alive → auto-retry up to 3 times, 800 ms apart, then FAILED.
       Failed + session dead  → PAUSED ("Connection lost") per INV-3.
       Paused                 → PAUSED, resumeOffset = bytesTransferred.
     Each file is wrapped in its own try/catch: a failure on file 3 of 6 logs,
     marks that item FAILED, and continues with 4–6. CancellationException is
     always rethrown unmodified; nothing else is allowed to reach the coroutine's
     default handler, which would crash both ends.

9.4  INTEGRITY AND DE-DUPLICATION.
     Sender SHA-256s files up to PREHASH_LIMIT = 256 MB (cached per item); larger
     files skip the pre-hash. On META the receiver checks whether an identical
     file (same sha) already exists at the destination → replies "already
     present" → sender marks SKIPPED ("identical file already present on
     receiver"). Every chunk is CRC32-verified on arrival; a CRC mismatch FAILS
     the file and is never "repaired" by appending — that yields a
     correctly-sized, silently corrupt file. Partial writes go to
     `<name>.morsecode.part`, are appended on resume, verified (size always, sha256
     except on the lowest tier), then atomically renamed to the final name.
     Orphan `.morsecode.part` files older than 24 h with no journal entry are
     deleted at startup.
     On the Nearby path, where the SDK hides chunking, the pre-payload metadata's
     size is compared on every tier and sha256 additionally except on the lowest.

9.5  CONFLICT POLICY. Evaluated on the RECEIVER, per full relative path (so
     AlbumA/img1.jpg and AlbumB/img1.jpg never collide), before the first byte
     hits the destination. Detection order: name → size → sha256 (sha only when
     needed, and skipped on the lowest tier with a log line).
     Dialog: [Overwrite] [Skip] [Keep both] + "Apply to all remaining conflicts
     in this batch". Keep both renames photo.jpg → photo (1).jpg → photo (2).jpg.
     Default policy = Rename duplicates (Settings, §6.13). A conflict dialog must
     not block unrelated items in the same batch from progressing.

9.6  BATCH UX. Every picker session is one batch (batchId). On terminal state the
     engine emits BatchCompleted and the UI shows EXACTLY ONE coalesced summary
     per batch window, ~2.5 s after the last activity: "N sent, N failed, N
     skipped — Average speed X MB/s", plus total bytes and elapsed time, with
     [Retry failed] (only when something failed) and [Done]. Never one popup per
     file. The summary is derived from the same TransferQueue the live rows used —
     never recomputed independently. SKIPPED is always reported distinctly from
     FAILED. Both directions record history through the SAME complete() path: a
     send that leaves no history row while the receive side has one is a defect.

9.7  RESTART RECOVERY. If an unfinished journal entry exists at launch, show
     "Resume interrupted transfer?" naming the peer and remaining items, with
     [Resume] and [Discard] — never silently resume, never silently discard. If
     the peer is not rediscovered within a short window, offer Discard with a
     plain explanation instead of hanging.

9.8  CONSENT AND SESSION END. Incoming connection → accept/reject popup (§6.16).
     Reject = clean REJECT, nothing written. Ending a session asks for
     confirmation. Minimising never ends a session.

10. BROADCAST ENGINE — ONE SENDER, MANY RECEIVERS   [NEW]
--------------------------------------------------------------------------------

10.1 MODEL. A broadcast is ONE TransferQueue fanned out to N PeerDelivery rows:
       PeerDelivery(peerId, peerName, avatarColor, sessionState, itemStates map,
                    bytesSent, speedBps, verified, lastError)
     The queue is authoritative for "what is being sent"; each PeerDelivery is
     authoritative for "how far that peer has got". The UI never derives a second
     copy of either.

10.2 FAN-OUT. One independent TransportSession per peer. The source file is
     opened once per peer (separate FileChannel positions) — do not try to share
     one stream across sockets. Chunk reads are scheduled round-robin so a slow
     peer cannot starve the others, with a per-peer send window; the file is
     considered done for a peer only when THAT peer CRC-verifies it.
     Peer cap: default 4, user-settable 2–8 (Settings → Transfer). On Nearby the
     cap is 3 (P2P_STAR) and the UI says "Nearby supports up to 3 phones — the
     rest will wait". Low-tier devices (§13) cap at 2 and say so.

10.3 INVARIANTS.
     INV-B1 PEER ISOLATION. A peer that rejects, drops, errors or is cancelled
       never fails the batch or any other peer. Its rows grey out with a reason
       and a [Retry peer] action.
     INV-B2 PER-PEER RESUME. resumeOffset is tracked per (file, peer). A peer
       that reconnects continues from its own offset; others are unaffected.
     INV-B3 NO GLOBAL HANG. INV-1/2/3 apply per peer session. The broadcast
       worker must never block on the slowest peer to start the next file for
       the fast ones.
     INV-B4 VERIFY EVERY PEER. "Broadcast complete" may only appear when every
       accepted peer has CRC/size-verified every file it accepted. If some peers
       failed, the header reads "Broadcast finished — 2 of 3 phones verified"
       with the failures listed. [GAP]
     INV-B5 ONE SUMMARY. One coalesced batch summary on the sender covering all
       peers, and one ordinary per-batch summary on each receiver.

10.4 STAT FORMULAS (these must match the mocks exactly):
       PEERS            = number of accepted peers                       (3)
       BATCH MB         = Σ size of every file in the queue              (212)
       TO SEND MB       = BATCH MB × PEERS                               (636)
       MB SENT          = Σ bytesSent across peers (what is on the wire so far)
       combined throughput = Σ per-peer speedBps                    (14.2 MB/s)
       deliveries       = files × accepted peers                           (9)
       FILES EACH       = number of files in the queue                     (3)
       avg speed        = MB SENT ÷ elapsed seconds
     While running, the three tiles are PEERS · BATCH MB · TO SEND MB; on
     completion they are PHONES · FILES EACH · MB SENT. (The mocks label both
     screens "TOTAL MB" with two different meanings — resolved here, Appendix D.)

10.5 RECEIVER SIDE. A receiver in a broadcast is an ordinary receiving session
     with `broadcast=true` in HELLO, which only changes the PeerCard subtitle
     ("Broadcast · Phone · LAN") and the [FROM] badge. Conflict policy, consent,
     integrity, journaling and history behave exactly as in 1:1.

10.6 HONESTY. If throughput per peer falls below ~40% of the single-peer
     baseline, the summary card adds "Speed is shared between 3 phones" rather
     than letting the user think something is broken.

11. TRANSPORTS AND WIRE PROTOCOL
--------------------------------------------------------------------------------

11.1 UNIFIED DISCOVERY [CHANGED]. One Discovery component runs every available
     mechanism at once and publishes ONE deduplicated peer list:
       - LAN: UDP beacons (below) whenever the phone is attached to any network,
         router or hotspot;
       - Nearby: advertise + discover when Play Services are available and the
         permissions are granted;
       - WebShare: every accepted browser session is published as a peer.
     Each peer carries its transport badge and address. The "TRANSPORT" row is a
     PREFERENCE (Auto / Wi-Fi LAN / Nearby), not a hard switch that hides half
     the network; Auto prefers LAN whenever the phone has a network, because
     Nearby never uses the shared infrastructure network — on old hardware it
     negotiates Bluetooth and is far slower. Manual host:port connect is always
     available as a third path. After 15 s with nothing found, offer the
     Connection Doctor and the other transport explicitly.

11.2 LAN TRANSPORT.
     Discovery : UDP broadcast on port 33457, one announce every 1200 ms
                 (deviceId, name, appId, protocolVersion, broadcast flag).
                 A MulticastLock is held while discovering.
     Data/serve: TCP 33456.
     Control   : one TCP connection carrying newline-terminated UTF-8 JSON —
                 HELLO → ACCEPT/REJECT → per-file META {name, relativePath, size,
                 mime, sha256, resumeOffset} → ACK, plus PAUSE_REQ, RESUME_REQ,
                 CANCEL, BYE, and PING/PONG keepalive.
     Data      : a separate TCP connection PER FILE. Per-chunk framing:
                 magic "MRSC" (4 B) | seq int32 | len int32 | payload | CRC32 int32
                 Chunk size 256 KB; reject len > 4× chunk size; tcpNoDelay = true;
                 read timeout 25 s guarded by an idle/progress watchdog.
     ** CRITICAL FRAMING RULE (regression-guarded) ** The first line (the JSON
     header) of a DATA connection must be read BYTE BY BYTE from the raw
     InputStream until '\n'. Never wrap a socket that will carry binary chunks in
     a BufferedReader before the header is consumed — its 8 KB pre-read swallows
     the first MRSC frame and produces "chunk magic mismatch — framing slipped".
     A BufferedReader is permitted only on pure-text branches (HELLO handling).
     Other rules that each encode a real production defect:
       - One shared mutex guards every read and every write on the control
         channel, and it is held across a write-then-read-reply pair as one
         atomic unit. A "busy" boolean is not sufficient.
       - Progress and completion advance only AFTER a successful flush().
       - Never force-cast a Socket to a SocketChannel; getChannel() is null for
         accept()/connect() sockets. Use buffered streams, or FileChannel
         transferTo/transferFrom against the stream's channel where available.
       - One data connection per file; never reuse one across files or across a
         direction turnaround — a stale socket looks connected and yields a
         zero-byte file with no error.
       - Idle is not closed: a read timeout means "nothing happened", never
         "peer gone". Only an explicit close/reset or a genuine I/O error ends a
         session.
     Resume  : the receiver reports its .part length in ACK; the sender seeks
               there and continues the seq numbering.

11.3 NEARBY CONNECTIONS TRANSPORT.
     Strategy P2P_STAR with a fixed service id; advertise and discover
     concurrently. Control messages use the same JSON vocabulary as small byte
     payloads; files travel as STREAM (or FILE) payloads — do not reimplement
     chunking here. A small metadata payload (name, size, sha256, relativePath,
     mime) precedes every file so §9.4's verification is possible.
     sendFile registers a CompletableDeferred per outgoing file keyed by fileId
     (outgoingWaiters), maps payloadId → fileId, and translates
     PayloadTransferUpdate: SUCCESS → Completed, FAILURE → Failed, CANCELED →
     Paused or Cancelled depending on the flag that was set, IN_PROGRESS →
     progress.
     SESSION-END RULE: onTransportDisconnected and close() must FIRST fail every
     outgoing waiter ("session closed") and clear the pause/cancel/payload maps
     before tearing anything down. This is what makes INV-1/INV-3 hold.
     Pause/cancel: send the control message, call cancelPayload, AND schedule the
     3 s terminal fallback.
     HONEST COPY: Nearby uses Bluetooth/Wi-Fi Direct, needs Play Services, does
     not use the router, and cannot pause mid-payload — the UI says "Pauses after
     the current file" there instead of implying an exact-offset pause it cannot
     deliver.

11.4 WEB PEER TRANSPORT. A WebPeerSession wraps an accepted browser session so
     the engine can treat it like any other peer (§7.8). Its sendFile publishes
     an offer over SSE and completes when the browser's ranged download finishes
     or times out; pause/cancel revoke the offer.

11.5 MANUAL PAIRING — NO QR ANYWHERE [CHANGED]. The product ships no QR
     scanner and no QR generator: no QrScanActivity, no camera permission, no
     ZXing dependency, no /api/qr route, no QR entry in the WebShare browser
     rail and no QR block on the WebShare phone screen. Pairing by address is
     the ONLY manual path, and it exists in exactly one place: the [Manual IP]
     button on the discovery screen (§6.3). It accepts `host`, `host:port` or a
     pasted `morsecode://host:port`, defaults to port 33456, validates before
     dialling and reports "Can't reach <host>:<port>" on failure.
     Everywhere an address is displayed (WebShare screen, WebShare browser
     header, Connection Doctor) it is large, monospaced and tap-to-copy, with a
     [Copy] affordance — copying the address is what a QR used to be for.
     RATIONALE: a scanner is only useful if the product also displays a code to
     scan; once the code is gone the scanner is a camera permission and a
     third-party decoder in exchange for nothing. Do not reintroduce either
     half — if a future release wants pairing codes back, it must add both, on
     purpose, with its own spec section.

11.6 PROTOCOL VERSIONING. HELLO carries protocolVersion. Mismatch → a readable
     "This phone runs an older version of Morsecode — update to transfer" rather
     than a framing error.

12. STORAGE, DESTINATIONS AND MEDIA LIBRARY
--------------------------------------------------------------------------------

12.1 ACCESS METHOD BY CONTENT TYPE.
       Photos/Videos/Music → MediaStore query/insert/update only. Never assume a
         raw path is writable on API 29+.
       General files/folders/SD/USB-OTG → Storage Access Framework
         (ACTION_OPEN_DOCUMENT_TREE + DocumentFile); every grant is persisted
         immediately with takePersistableUriPermission so nothing is re-asked.
       Other apps' /Android/data/<pkg> → out of scope, unreachable, never
         claimed in UI.

12.2 GRACEFUL DENIAL. A folder that cannot be read because of scoped storage
     must be detected as a DISTINCT condition from "zero children" and must
     render "Access needed to view this folder — Grant access" with a button
     that opens SAF scoped to that location. Silently rendering an empty folder
     is release-blocking (it is indistinguishable from a real empty folder).

12.3 ALL-FILES ACCESS. MANAGE_EXTERNAL_STORAGE is offered only as an explained
     optional toggle in Settings → Storage access, with a plain-language
     rationale sheet before the system screen, and only where policy permits.
     Never at first run, never bundled into the permission flow.

12.4 DESTINATIONS. Default download location is user-selectable. The default is
     Download/Morsecode, created on first receive (§1.1.1). If the user picks a
     different folder, everything — receives, "Open folder", the Files tab and
     the WebShare upload target — follows that choice; the app never writes to
     two destinations at once. Received media is additionally indexed into MediaStore so
     galleries see it. "Open folder" on the completion screen opens the
     destination through the system file viewer, falling back to the in-app
     Files tab at that path.

12.5 MEDIA LIBRARY. MediaLibrary backs categories PHOTOS / VIDEOS / MUSIC /
     DOCUMENTS / APPS (+ Ebooks, Archives, APKs, Large files) and folderInfo()
     (name, count, size) for the folder panels. Apps come from PackageManager
     (icon, label, APK path, size); declare <queries> for package visibility.
     INV-9 ORDERING: sort by date-taken falling back to date-modified, as a SQL
       expression `CASE WHEN DATE_TAKEN > 0 THEN DATE_TAKEN ELSE DATE_MODIFIED *
       1000 END` with `_ID DESC` as tiebreak, so day headers appear exactly once,
       in order.
     INV-10 PAGINATION: never put LIMIT/OFFSET inside the MediaStore sort string
       (Android 14's MediaProvider rejects it: "Invalid token LIMIT"). Open the
       cursor, moveToPosition(offset), then read `limit` rows in a do-while.
       Page size follows DeviceTier.
     DATE UNITS: DATE_TAKEN is MILLISECONDS; DATE_ADDED and DATE_MODIFIED are
       SECONDS. Mixing them sends files to 1 Jan 1970 in every gallery. Comment
       the unit at every call site. Below API 29 never use
       MediaStore.Images.Media.insertImage() for a received image — it writes no
       DATE_TAKEN and re-encodes the bitmap, destroying quality and EXIF; insert
       via ContentResolver.insert() with fully populated ContentValues and stream
       the original bytes.
     Lists are cursor/page-backed (10 000-item folders must scroll smoothly on
     the reference phone); thumbnails load lazily with bind tokens (§6.9.2) and a
     tier-scaled LRU cache.

16. DIAGNOSTICS AND LOGGING
--------------------------------------------------------------------------------

16.1 The log captures Morsecode's own lines plus crash-relevant platform lines
     only — never an unfiltered dump of every process.
16.2 Lines are written to a persistent in-app file (ring buffer), not only to
     logcat. "Clear" records the moment it happened, deletes the app's own file,
     and filters anything older from sources it does not own.
16.3 Export produces one .txt headed "Morsecode <version> (<versionCode>)"
     containing the log and every stored crash report, shareable through a
     FileProvider from Settings and from the crash dialog.
16.4 EVERY handshake step (META sent, ACK/resume received, data connection
     opened, file start, file complete), every pause/resume transition, every
     conflict decision, every consent accept/reject, and every per-peer
     broadcast event is logged WITH A TIMESTAMP at the moment it happens — not
     summarised afterwards. This is what makes a stall diagnosable in seconds.
16.5 Any byte or progress figure shown in logs or UI must be read from the real
     underlying state (e.g. the .part file's actual length), never from a
     side-counter that some code path forgets to update.
16.6 Crash reports are captured by an uncaught-exception handler, stored
     locally, listed in the log viewer, and NEVER uploaded. The Settings switch
     controls local capture only; its subtitle says "Local · never uploaded".

20. ENGINEERING RULES AND DEFECT PREVENTION
     (Each line below is a defect that actually shipped once. Do not re-earn it.)
--------------------------------------------------------------------------------

20.1 SINGLE SOURCE OF TRUTH, EVERYWHERE.
     - Tab index drives both the active indicator and the rendered dataset. A
       tab that looks active while another category's data shows underneath can
       make someone send the wrong file — release blocker.
     - Selection has ONE canonical set read by the renderer and by the send
       queue. Clearing it clears it everywhere, including a queue already handed
       off. A fresh send screen never shows stale ticks.
     - TransferQueue is the one source for the queue view, the notification and
       the batch summary. No derived copies.
     - Broadcast: the queue owns files, PeerDelivery owns per-peer progress.

20.2 ASYNC INTO RECYCLED VIEWS. Every async load bound to a RecyclerView row
     carries a bind token verified before the result is applied — photos,
     videos, apps, music, documents, peer avatars, all of them.

20.3 EVENTS vs STATE. One-shot signals use a consumable wrapper; LiveData
     replaying a stale value must never re-trigger navigation. Observable
     connection state must distinguish "never connected" from "was connected,
     now closed".

20.4 EXPLICIT INTENT IN NAVIGATION. Screens receive their purpose as an
     argument; nothing is inferred from incidental state.

20.5 REACHABILITY. A helper written for an edge case is not a fix until the
     calling path actually reaches it — verify the earlier `return` no longer
     short-circuits past it.

20.6 HONEST CAPABILITY. Never label something the transport cannot do (exact
     pause on Nearby, simultaneous STA+AP, access to another app's sandbox,
     "instant" anything). Say what will really happen.

20.7 CROSS-MODULE RULES (dormant while the build is single-module; binding the
     moment it is split): shared resources live in the shared module; a module
     that injects from another declares a direct dependency on it; making a
     function `suspend` propagates to every caller in the same change.

20.8 LINT GATE (must run in CI and fail the build):
     - unresolved resource references from the referencing module's view;
     - Java-8 default collection methods without an SDK_INT >= 24 guard;
     - more than one companion object per class; nested data classes inside
       inner class bodies; coroutine extensions used without their import;
     - interactive views without contentDescription (or an explicit decorative
       marker); touch targets under 48 dp;
     - hardcoded hex colours in layouts/Kotlin outside the token file;
     - user-visible string literals outside strings.xml.

20.9 KOTLIN/LANGUAGE CONSTRAINTS. No nested data class in an inner class body;
     at most one companion object; every coroutine extension explicitly
     imported; no NDK anywhere in the transfer engine (the bottleneck is I/O,
     not the JVM).

20.10 PERFORMANCE AS CORRECTNESS. Category counts that take minutes, a list that
     stutters at 10 000 items, a zip download that shows nothing for 30 s while
     the archive is built in memory — all are defects, not "inherent".

APPENDIX D — GAPS FOUND IN THE MOCKS AND THE DECISION TAKEN
================================================================================
 G1  Broadcast stat tiles were labelled "TOTAL MB" on both the in-progress sheet
     (212 = batch size) and the completion sheet (636 = aggregate). Renamed to
     BATCH MB / TO SEND MB while running and PHONES / FILES EACH / MB SENT on
     completion. Formulas fixed in §10.4.
 G2  One receive sheet shows a single summary line mixing "3 received" with a
     "Sending back" section. Split into "In:" and "Out:" lines (§6.6).
 G3  The Settings sheet shows only a "Dark mode" switch, but the product needs
     "Follow system". Added as a second switch that disables and mirrors the
     first (§6.13).
 G4  Several Files sheets show only four tabs; others show five. Five tabs is
     canonical: Photos · Videos · Music · Apps · Files (§6.9).
 G5  No mock shows how a broadcast is STARTED. Defined: Send → long-press /
     overflow → "Broadcast to several phones", plus multi-select in discovery
     (§6.3, §6.8.1).
 G6  No mock shows peer rejection or failure during a broadcast. Defined:
     greyed row + reason + [Retry peer]; header degrades to "Broadcast finished
     — 2 of 3 phones verified" (INV-B4).
 G7  No maximum peer count is shown. Default 4, range 2–8, Nearby 3, low-tier 2,
     exposed in Settings (§10.2, §6.13).
 G8  The Viewer's five bottom actions are unlabelled. Defined as Share · Edit ·
     Delete · Info · Send, with Edit hidden when no ACTION_EDIT handler exists
     (§6.10).
 G9  The music player shows both "Save" and "Liked". Defined: Save = add to a
     local playlist; Liked = local favourite toggle. Both on-device only (§6.11).
 G10 The WebShare video player mock uses the hotspot address 192.168.43.1 while
     the rest use 192.168.1.24. Both topologies are supported; the URL shown is
     always whatever address the server is actually bound to (§7.1).
 G11 "Office Laptop · WebShare" appears in the phone's discovery list, implying
     phone → browser push, which had no protocol. Defined in §7.8 (SSE offer +
     ranged download) and §11.4 (WebPeerTransport).
 G12 The mocks show a QR entry in the WebShare rail, a QR block on the WebShare
     phone screen and a [Scan QR] button on the discovery screen. DECIDED
     (product direction, overrides the artwork): QR is removed from the product
     entirely — scanner, generator, route, rail entry and buttons (§11.5).
     Pairing by address happens in ONE place, [Manual IP] on the discovery
     screen, and every displayed address is tap-to-copy instead. Mock frames
     showing a QR are stale artwork, like the wordmark (§0.3.1).
 G13 The CC button in both video players had no defined source. Defined:
     embedded or sidecar .srt only, otherwise disabled with "No subtitles".
 G14 The mock decks show device frames, deck captions and a Dark/Light pill.
     These are presentation chrome and must not be implemented (§0.4).
 G15 Product naming and identity: the mock deck and both reference drafts were
     drawn for an earlier product, "MorseLink" (applicationId
     com.morselink.app, 1.5.x). This is a separate, greenfield project. DECIDED:
     the product, repo, package, wire magic, URL scheme, temp-file suffix and
     media folder are all "morsecode" (§1.1.1); the first build is 1.0.0 (1);
     there is no installed base, so no migration, no legacy scheme, no legacy
     .part handling and no cross-product interop requirement exists — and none
     may be invented. The mocks' "MorseLink" wordmark and their "1.5.1 (15)"
     sample log line are stale artwork, not requirements (§0.3.1). A19 is the
     acceptance criterion.
